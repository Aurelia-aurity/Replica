# 백엔드↔AI baseline 호출 계약 초안

상태: **담당자 합의 전 초안**, 2026-10-10, [이슈 #15](https://github.com/Aurelia-aurity/Replica/issues/15).
이 문서는 앞으로 백엔드가 AI에 보낼 값과 받을 결과를 제안합니다.
현재 CLI에 HTTP API·대화 이력 처리가 구현되어 있다는 뜻은 아닙니다.
실제 서버·클라이언트 구현, GPU 운영, 학교 접속 허가는 이 문서의 검증 대상이 아닙니다.

## 1. 범위와 담당 경계

baseline은 개인화 없이 텍스트 답변을 생성합니다. 음성 입력은 별도 STT 파트에서
처리한 텍스트로 전달하며, TTS 연결도 별도 계약입니다.
최근 대화는 문맥으로만 사용하고 대상 인물의 원본 기록·경험 근거와 구분합니다.
생성 답변을 개인화 학습 자료로 자동 편입하지 않습니다.

| 항목 | 이번 초안의 제안 | 합의 상태 |
| --- | --- | --- |
| 호출 형태 | 비스트리밍, 완성된 답변 1회 반환 | 사용자 선택, 담당자 합의 대기 |
| 대화 이력 | 최근 완결 user/assistant 쌍 포함, 오래된 쌍부터 제외 | 사용자 선택, 담당자 합의 대기 |
| 동시 생성 | AI 인스턴스당 1건, 대기열 없음 | 사용자 선택, 담당자 합의 대기 |
| 백엔드 | 사용자 인증·권한 확인, 허용된 이력 조회, 요청 ID 발급, 결과 연결 | 윤서준·DB 관련 임재성 확인 필요 |
| AI | 입력 검사, 문맥 한도 검사, 답변 생성, 고정 오류 반환 | 김태환·윤서준 확인 필요 |
| 저장·조회 | user/conversation과 request_id의 연결은 백엔드 내부 관리; AI는 DB 조회 없음 | 임재성 확인 필요 |
| 숫자 한도 | 아래 한도 표의 제안값 | 담당자 합의·모델 확인 필요 |
| 연결·보안 | 서비스 인증, 암호화된 전송, 허용된 호출자 제한 | #14 학교 확인·담당자 합의 필요 |
| 시간 제한 | 백엔드 전체 대기시간과 AI 추론 마감 별도 정의 | 수치·전달 방법 미정 |

이번 요청에는 `user_id`, `conversation_id`, `persona_id`, `system_prompt`,
원본 기록이나 검색 근거를 넣지 않습니다. 백엔드는 앱 사용자를 확인하고 허용된
대화만 구성합니다. AI 호출 인증은 앱 사용자 인증과 별개이며 앱 자격증명을 전달하지 않습니다.
AI는 호출 간 대화 상태를 저장하지 않습니다. 실행 중 요청 ID의 추적은 중복 처리용입니다.

수행계획서의 말투 프로필·RAG는 후속 개인화 단계에 적용합니다. 개인 경험·관계·사실은
원본 기록의 근거가 필요하고 일반 대화에는 말투를 적용할 수 있다는 방향을 유지합니다.
그 기능을 이 baseline이 제공한다고 표시하지 않습니다. 향후 분석·프로필·색인 생명주기와
개인화 대화는 별도 버전 계약으로 정의합니다. 1명 기준 시제품의 여러 인물 확장도 그때 다룹니다.

## 2. 요청

제안 경로: `POST /v1/baseline/generate`, 본문 `Content-Type: application/json`.
호스트·포트·인증 헤더·인증 방식은 미정입니다. 아직 호출 가능한 URL은 없습니다.
서비스 인증 실패는 본문 파싱 전에 판정합니다(원시 본문 크기 검사는 그보다 먼저).

```json
{
  "request_id": "11111111-1111-4111-8111-111111111111",
  "message": "아까 추천한 방법을 다시 설명해 줘.",
  "history": [
    {"user": "오늘 공부를 어떻게 시작할까?", "assistant": "작은 목표 하나부터 정해 봐."}
  ],
  "max_new_tokens": 160
}
```

| 필드 | 규격 |
| --- | --- |
| `request_id` | 백엔드가 새 사용자 요청마다 발급하는 소문자·하이픈 포함 UUID, 길이 36 |
| `message` | 현재 사용자 텍스트, 공백만 있는 값 불가 |
| `history` | 오래된 순서의 완결 대화 쌍 배열; 없으면 `[]`를 명시 |
| `history[].user`, `.assistant` | 각각 공백만 있는 값 불가; 중간 생성·실패 응답은 포함하지 않음 |
| `max_new_tokens` | 출력 토큰 예산, 정수 1~1024; 백엔드 기본값 제안 160 |

네 필드는 모두 필수입니다. 기본값은 백엔드가 채웁니다. JSON Schema는 값을 삽입하지 않습니다.
정의되지 않은 필드는 모든 객체에서 거부합니다. caller가 system/tool 역할이나 임의 옵션을
넣을 수 없습니다. 고정 system prompt·모델·tokenizer는 AI 내부 설정입니다.

| 제한 | 제안값 | 초과 결과 |
| --- | --- | --- |
| 원시 HTTP 본문 | 256 KiB = 262144 바이트 | 413 |
| 현재 질문 | 16000 Unicode code point | 413 |
| 대화 이력 | 20쌍 | 413 |
| 이력의 각 user/assistant 텍스트 | 각각 16000 Unicode code point | 413 |
| 출력 토큰 예산 | 1~1024, 기본 160 | 범위 오류 400 |
| 실제 입력+출력 문맥 | 실제 모델·tokenizer의 유효 한도 | 이력 제외 후에도 초과하면 422 |

문자 수와 UTF-8 바이트 수, 모델 토큰 수는 서로 다릅니다. 본문 크기는 파싱 전 수신 본문의
바이트 수로 검사합니다. 압축 본문 등의 추가 전송 형식은 이 초안에 정의하지 않습니다.
16000자·출력 예산은 현재 CLI 제한을 참고한 제안이며 HTTP·이력 한도는 신규 제안입니다.

## 3. 이력 축소와 성공 응답

실제 tokenizer로 다음을 검사합니다.

```text
token_count(render(고정 system prompt + 유지한 완결 이력 쌍 + 현재 질문
                   + chat template/generation prompt 부가분))
  + max_new_tokens <= 유효 모델 문맥 한도
```

초과하면 가장 오래된 **쌍 전체**를 제거하고 다시 렌더링·토큰 계산합니다.
현재 질문과 출력 예산을 몰래 줄이지 않습니다. 이력이 없어도 넘으면 422를 반환합니다.
본문·구조·문자 수 상한은 이력 축소 전에 검사하므로 축소로 우회할 수 없습니다.

HTTP 200:

```json
{
  "request_id": "11111111-1111-4111-8111-111111111111",
  "message": "우선 짧게 끝낼 수 있는 목표 하나를 정하고 시작해 봐.",
  "finish_reason": "stop",
  "ai_generated": true,
  "context": {"used_history_turns": 1, "dropped_history_turns": 0}
}
```

`message`는 assistant의 완성 텍스트이며 공백만 있는 출력은 성공으로 취급하지 않고
`INFERENCE_FAILED`로 처리합니다. `finish_reason`은 `stop`(정상 종료) 또는
`length`(출력 예산 소진)입니다. `length`도 200이며 백엔드는 이를 보존합니다.
`ai_generated`는 반드시 `true`입니다. 원본 질문·이력·프로필·검색 근거를 응답에 복사하지 않습니다.

두 context 값은 0 이상의 정수이고 다음 조건을 만족해야 합니다.

```text
used_history_turns + dropped_history_turns = 제출한 history 배열 길이
```

여기서 turn은 user/assistant 한 쌍입니다. 응답의 request_id는 요청과 같아야 합니다.

## 4. 오류 응답과 판정 순서

```json
{
  "request_id": "11111111-1111-4111-8111-111111111111",
  "error": {"code": "AI_BUSY", "message": "AI가 다른 요청을 처리 중입니다."}
}
```

| HTTP | 고정 `error.code` | 의미 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | JSON 파싱, 필수 필드, 형태·타입·UUID·범위·공백·미정의 필드 오류 |
| 401 | `SERVICE_UNAUTHENTICATED` | 서비스 인증 실패 |
| 403 | `SERVICE_FORBIDDEN` | 인증된 서비스 호출자에게 권한 없음 |
| 413 | `PAYLOAD_TOO_LARGE` | 원시 본문·질문·이력 텍스트·이력 쌍 수 상한 초과 |
| 422 | `CONTEXT_LIMIT_EXCEEDED` | 이력 축소 후에도 모델 문맥 초과 |
| 503 | `MODEL_NOT_READY` | 모델 준비 안 됨 |
| 409 | `REQUEST_IN_PROGRESS` | 같은 인스턴스에서 동일 ID가 실행 중 |
| 429 | `AI_BUSY` | 다른 ID가 생성 슬롯을 사용 중 |
| 504 | `INFERENCE_DEADLINE_EXCEEDED` | AI가 추론 마감 초과를 알리는 오류를 실제 반환 |
| 500 | `INFERENCE_FAILED` | 추론 실패 또는 빈 출력 |

오류 메시지는 위 의미의 안전한 안내문입니다. 분기는 메시지 내용 대신 HTTP와 code로
처리합니다. 원시 예외·traceback·프롬프트·이력·개인 기록·자격증명을 응답이나 로그에 넣지 않습니다.

판정 순서는 **원시 바이트 상한(413) → 서비스 인증(401/403) → 파싱 및
구조·타입·형식·범위(400) → 파싱된 텍스트/쌍 수 상한(413) → 모델 준비(503)
→ 축소 후 문맥(422) → 원자적 요청 수락(409/429)**입니다.
유효한 요청의 수락 시 같은 ID 실행 중이면 409가 우선이고, 그 외 슬롯 사용 중이면 429입니다.
거부된 요청은 생성을 시작하지 않습니다. ID·슬롯 확인과 예약/반환은 원자적으로 처리해야 합니다.

스키마는 모든 길이 상한을 포함합니다. HTTP 분류에서는 길이·쌍 수 상한 오류를 413으로
구분하며, 함께 있는 형태·타입 등의 오류가 400보다 뒤의 파싱된 상한 오류보다 우선합니다.
예: 너무 긴 message와 미정의 필드가 함께 있으면 400, 상한 초과만 있으면 413입니다.
단, 원시 바이트 상한 초과는 파싱 전에 413입니다. 이 순서는 향후 구현의 요구사항입니다.

### 응답 ID와 안전하게 얻지 못한 ID

성공뿐 아니라 오류도 원 요청 ID와 대조합니다. 유효 요청 파싱 후의
409/429/422/500/503/504는 원 ID를 반환해야 합니다. 파싱된 400/413도 request_id를
안전하게 검증할 수 있으면 해당 ID를 반환합니다. 전체 요청이 유효하지 않아도 ID 자체가
정의된 UUID로 안전하게 추출되면 가능합니다.
인증 거부·파싱 전 원시 413·깨진 JSON·누락/잘못된 ID처럼 안전하게 얻지 못한 경우에만
`request_id: null`을 허용합니다. 인증 거부에서는 ID를 얻기 위해 본문을 파싱하지 않습니다.

ID 불일치 또는 허용되지 않은 null은 정상 답변이나 그 요청의 AI 오류로 저장하지 않고
**프로토콜/상관관계 실패, 결과 UNKNOWN**으로 취급합니다. 자동 재시도하지 않습니다.
허용된 초기 null 오류는 이 HTTP 호출의 초기 거부일 뿐 특정 ID의 실행 종료를 증명하지 않습니다.

## 5. 타임아웃·중복·재시도·취소

| 상황 | 계약상 의미와 책임 |
| --- | --- |
| 실제 수신·검증한 AI 504 | 추론 마감 초과 안내. 계산 종료나 슬롯 반환을 뜻하지 않음 |
| 백엔드 연결/읽기/전체 타임아웃·연결 끊김 | AI envelope 없는 전송 실패, 결과 UNKNOWN. AI 504를 만들어 귀속하지 않음 |
| HTTP 종료 후 계산 계속 | AI는 실제 계산이 끝날 때까지 ID·슬롯을 보유; 연결 종료만으로 반환 금지 |
| 같은 실행 중 ID 다시 수신 | 단일 인스턴스 추적 범위에서 409, 신규 생성 없음 |
| 종료된 ID, 재시작, 여러 인스턴스 | 중복 방지·결과 재조회 보장 없음 |
| 재시도 | 자동 재시도 없음. 백엔드는 요청별 단일 호출을 조정하고 UNKNOWN 후 재전송하지 않음 |
| 새 사용자 요청 | 새 ID 발급. 이전 계산 중이면 거부될 수 있음 |
| 취소 | 취소 endpoint·중단 보장 없음. HTTP 타임아웃은 GPU 중단 명령이 아님 |

request_id는 상관관계 ID이며 영속 idempotency 키가 아닙니다. 자동 재시도는 영속 중복 방지와
결과 조회 계약을 별도로 마련하기 전까지 도입하지 않습니다. 시간 제한 수치·전달 방식은 GPU
측정과 담당자 합의 후 정합니다. 본 초안에는 임의 초 값을 넣지 않았습니다.

## 6. 관리 원본과 합성 검증

구조 규격의 관리 원본은 `request.schema.json`, `success.schema.json`, `error.schema.json`입니다.
JSON Schema draft 2020-12를 사용합니다. 필드·제약 변경은 스키마와 이 설명·예제를 함께 수정합니다.
HTTP/code 대응, 오류 우선순위, 요청-응답 ID 일치와 context 합은 문서의 의미 규칙으로
별도 검사합니다. OpenAPI나 서버 모델을 병행 원본으로 만들지 않았습니다.

`examples/*.json`은 합성 HTTP 요청/응답 fixture입니다. `conditions`는 실제 서버에서 나온
측정값이 아니라 문서상 분기 조건이고 `request_valid`는 구조 스키마의 기대값입니다.
일반 호출, 보존/축소된 이력, length 종료, 잘못된 입력, 미준비·중복·처리 한도·추론 실패,
인증 거부·문맥 초과·AI 504와 envelope 없는 전송 타임아웃을 다룹니다.

```bash
python3 -m pip install -r contracts/requirements-test.txt
python3 -m unittest discover -s contracts/tests -v
```

검사는 스키마/합성 fixture 및 경계 조건을 확인합니다. 실제 HTTP 인증·원자적 슬롯 처리·
tokenizer 축소·GPU 성능·백엔드 타임아웃을 구현하거나 검증하지 않습니다.

## 7. 합의 전에 남은 항목

김태환·윤서준은 경로/필드·숫자 한도·오류 분류·시간 제한·중복/재시도 책임과 서비스 인증을
확인해야 합니다. 임재성은 사용자/대화와 요청 ID의 연결, 권한 확인 후 이력 조회 경계를
확인해야 합니다. 학교의 운영·접속 조건은 #14 문의 결과가 필요합니다.
이 합의 전에는 초안을 확정 규격이나 이슈 완료로 표시하지 않습니다.
