# SC-07 말투 프로필 · SC-13 프로필 만들기·이름 수정 · 홈 대화 상대 카드

이슈 #94의 프론트엔드 구현입니다. 기준은 `레플리카 화면 기획서_ver.2`(SC-02·SC-07·SC-13), `contracts/app-backend/api-spec.md`, 그리고 아직 병합되지 않은 계약 합의안 PR #117입니다. 백엔드·`contracts/`·DB는 변경하지 않았습니다.

**범위의 변화.**
- **2026-11-12**: 말투 프로필을 이번 버전에서 빼기로 했습니다. 그래서 SC-07과 이름 수정을 코드에서 지웠습니다. 지운 구현은 이 브랜치의 커밋 `df1a2e7`·`5ae684f`(리베이스 전 `3015633`·`b986a9b`)에 남아 있습니다.
- **2026-11-14**: PR #117 댓글에서 앱이 호칭 수정, SC-07 분석, `provider_address` 편집을 맞추기로 했습니다. 그래서 다시 넣었습니다.
  - 대화 상대의 호칭 필드와 수정 요청
  - SC-13 이름 수정 모드
  - SC-07: PR #117의 `{profile, analysis}` 조회와 분석 재요청에 맞춰 새로 작성
- SC-07이 쓰는 API는 모두 PR #117의 **제안**이며, 백엔드에 아직 라우트가 없습니다(아래 '서버와의 통신').

## 화면과 흐름

- **홈 대화 상대 카드(SC-02)**
  - 대화 상대가 있으면 이름, "말투 프로필 >"(SC-07로 이동), 텍스트·음성 대화 버튼을 보여 줍니다.
  - 대화 상대가 여러 명이면 이름 자리가 선택 목록이 됩니다.
  - 대화 상대가 없으면 "프로필을 만들어 주세요"와 "프로필 만들기" 버튼만 보여 줍니다.
  - 목록을 불러오는 중에는 진행 표시를, 실패하면 "대화 상대를 불러오지 못했어요."와 "다시 시도"를 보여 줍니다.
- **SC-13 프로필 만들기**
  - 카드의 "프로필 만들기"로 들어옵니다. 저장하면 새 상대의 SC-07로 이동하고(이슈 #94), 뒤로 가면 홈입니다.
  - 앞뒤 공백은 제거하고 최대 50자입니다(사용자가 보는 글자 수 기준, 이모지도 한 글자). 비었거나 공백뿐이면 저장 버튼이 비활성입니다.
  - 저장 중에는 저장·취소·뒤로가 막혀 중복 요청이 없습니다. 실패하면 입력값을 유지한 채 하단 알림과 "다시 시도"를 보여 줍니다.
  - 취소·뒤로 가기는 아무것도 저장하지 않습니다.
- **SC-13 이름 수정**: SC-07의 "대화 상대 이름 수정"으로 들어오는 같은 화면의 수정 모드입니다(`PersonaNameScreen(editing: …)`, `openPersonaRename`).
  - 제목은 "대화 상대 이름 수정"이고, 입력칸에는 지금 보이는 이름(`display_name`, 없으면 `name`)이 채워져 있습니다.
  - 저장하면 `PATCH /personas/{id}`로 `display_name`만 보냅니다. 처음 정한 `name`, `provider_address`, 기록은 그대로입니다.
  - 이름을 바꾸지 않고 저장하면 요청 없이 돌아갑니다.
  - 입력 규칙, 저장 중 잠금, 실패 시 입력 유지와 "다시 시도", 취소·뒤로 가기는 만들기와 같습니다. 같은 수정은 다시 보내도 결과가 같으므로 재시도에 별도 id가 없습니다.
  - 저장 후 SC-07로 돌아오면 제목("○○의 말투")이 새 이름으로 바뀌고 "대화 상대 이름을 저장했어요."가 나옵니다.
- **SC-07 말투 프로필**: 아래 'SC-07 상태' 참고.
- **대화 화면(SC-09·SC-10)**
  - 상단 제목은 대화 상대의 보이는 이름입니다. 대체 제목('엄마'·'대화')은 없습니다.
  - 이름을 확인할 수 없으면 대화를 시작하거나 열지 않고 "대화 상대를 확인할 수 없어요. 홈에서 대화 상대를 확인해 주세요."만 보여 줍니다.

## SC-07 상태

SC-07은 열 때마다 `GET /personas/{id}/style-profile`을 한 번 부릅니다(`StyleProfileController`). 아래로 당기면 다시 조회합니다.

**화면 구성**
- 위에서부터: "○○의 말투", 프로필이 있으면 "10월 6일 갱신", "나를 부르는 호칭" 카드, 상태별 내용.
- 아래에 고정된 버튼: "대화 상대 이름 수정"과, 필요할 때만 "다시 분석".

**상태별 내용.** 서버 응답의 `profile`(`ready` 프로필만, 없으면 `null`)과 `analysis`(마지막 분석 작업)를 함께 읽어 정합니다(`profileViewOf`).

| `profile` | `analysis` | 화면 | "다시 분석" |
| --- | --- | --- | --- |
| 있음 | 없음·`succeeded` | 자주 쓰는 표현·호칭·문장 끝맺음. 빈 항목은 "추출된 항목이 없어요" | 없음 |
| 있음 | `running` | 항목 + "새 기록으로 말투를 다시 분석하고 있어요. 대화는 지금 프로필로 계속돼요." | 없음 |
| 있음 | `failed` | 항목 + "말투를 다시 분석하지 못했어요. 지금 프로필은 그대로 쓰여요." | 있음 |
| 있음 | `unknown` | 항목 + "마지막 분석 결과를 확인하지 못했어요…" | 있음 |
| 없음 | 없음 | "아직 분석한 기록이 없어요" + "기록 올리기" | 없음(첫 분석은 서버가 기록 확정 때 시작) |
| 없음 | `running` | "말투를 분석하고 있어요" | 없음 |
| 없음 | `failed`·`insufficient_input` | "말투를 파악하려면 기록이 더 필요해요" + "기록 올리기" | 있음 |
| 없음 | `failed`·`source_changed` | "분석하는 동안 기록이 바뀌었어요" | 있음 |
| 없음 | `failed`·기타 | "말투를 분석하지 못했어요" | 있음 |
| 없음 | `unknown` | "분석 결과를 확인하지 못했어요" | 있음 |
| 없음 | `succeeded` | "프로필을 새로 만들어야 해요"(기록이 바뀌어 `stale`이 된 것으로 해석) | 있음 |

`error_code` 원문은 화면에 보이지 않습니다.

**`stale` 해석.** 계약상 `stale` 프로필도 `profile: null`로 옵니다. PR #117 댓글에서 앱이 "재분석 필요"를 알 수 있게 해 달라고 요청했고, 답은 아직 없습니다. 그동안 "분석은 성공했는데 프로필이 없다"를 `stale`로 해석합니다. 기록이 바뀌면 서버가 분석을 자동으로 시작하므로, 보통은 `running`으로 보입니다.

**다시 분석**(`POST /personas/{id}/style-profile/analysis`)
- 앱이 만든 `operation_id`를 보냅니다. 응답 없이 끊긴 요청(시간 초과·연결 끊김)만 같은 id로 다시 보내고, 그 밖의 결과 뒤에는 새 id를 씁니다.
- 요청 중에는 버튼이 "요청하는 중…"으로 잠깁니다.
- 결과에 따른 안내:
  - 성공하면 "말투 분석을 다시 시작했어요."가 나오고 분석 중 상태로 바뀝니다.
  - `unknown`을 서버가 확인해 이미 게시됐다고(`succeeded`) 답하면 "분석이 이미 끝나 있었어요."를 보여 주고 프로필을 다시 조회합니다.
  - 422는 "확정된 기록이 없어요. 기록을 올려 확정한 뒤 다시 시도해 주세요.", 404는 "대화 상대를 찾을 수 없어요.", 그 밖의 실패는 "분석을 요청하지 못했어요. 다시 시도해 주세요."입니다. 화면 상태는 그대로 둡니다.

**분석 중 상태 확인(앱 임시값).**
- 분석이 `running`이면 SC-07이 열려 있는 동안 **15초마다 최대 40번(10분)** 조용히 다시 조회합니다. 실패해도 보이던 내용은 유지합니다.
- 상한에 닿으면 자동 확인을 멈추고 "상태 다시 확인" 버튼을 보여 줍니다.
- 화면을 나가면 멈춥니다.
- 주기와 상한은 계약에 없어 앱이 정한 임시값입니다(`analysisCheckInterval`, `analysisCheckLimit`). PR #117 댓글에서 정해 달라고 요청했습니다.

**나를 부르는 호칭(`provider_address`).**
- PR #117에서 제안한 편집 위치인 SC-07에 두었습니다.
- 카드에 값 또는 "아직 정하지 않았어요"를 보여 줍니다. "수정"(값이 없으면 "정하기")을 누르면 하단 시트가 열립니다(`ProviderAddressSheet`).
- 시트 동작:
  - 최대 50자이며, 비우고 저장하면 지웁니다(`null`).
  - 프로필의 `address_terms`를 "기록에서 찾은 호칭"으로 보여 줍니다. 눌러야만 입력칸에 들어가고, 자동으로 채우지 않습니다. 분석 결과가 사용자 편집값을 덮어쓰지 않는다는 계약을 따른 것입니다.
  - 바뀐 것이 없으면 저장이 비활성입니다.
  - 저장 중에는 잠기고, 실패하면 시트와 입력값을 유지한 채 오류를 보여 줍니다.
  - 저장되면 "나를 부르는 호칭을 저장했어요."가 나옵니다.

**기록 올리기.** "기록 올리기"를 누르면 그 대화 상대의 SC-04(기록 올리기) 화면이 열리고, SC-07로 돌아오면 말투 프로필을 조용히 다시 조회합니다.

**기록은 대화 상대별입니다.** 계약에서 기록은 `persona_id` 하나에 속하므로, 홈은 대화 상대마다 기록 서비스와 기록 상태(`RecordController`)를 따로 만듭니다.
- 기록 탭과 SC-04는 홈에서 고른 대화 상대의 기록만 다룹니다. 대화 상대가 여러 명이면 기록 탭 위에 "OO의 기록"을 표시합니다.
- 다른 대화 상대를 고르면 그 상대의 기록 상태로 바뀝니다. 한 상대의 목록 응답이 다른 상대의 화면에 섞이지 않습니다. 같은 로그인 동안에는 상대별 서비스를 다시 쓰므로, 되돌아가면 그 상대의 미리보기 기록이 남아 있습니다.
- 대화 상대가 없으면 기록 탭은 "기록은 대화 상대별로 모여요"와 "프로필 만들기"를 보여 줍니다.
- 계정 삭제는 대화 상대와 상관없는 작업입니다. 대화 상대가 없을 때는 계정 전용 기록 서비스(대화 상대 id 없음)로 진행하고, 대화 상대 목록을 불러오는 동안에는 잠시 비활성입니다.
- `ReplicaApp.recordServiceFactory`는 대화 상대 id를 받습니다. 계정 전용일 때는 `null`을 받습니다.

## 서버와의 통신

| 통신 | 언제 | 보내는 것 | 서버 상태 |
| --- | --- | --- | --- |
| `GET /personas` | 홈 진입, "다시 시도" | 토큰만 | 구현됨 |
| `POST /personas` | SC-13 만들기 저장 | `name`, `persona_id` | 구현됨 |
| `GET /personas/{id}` | 만들기 저장 응답이 불확실할 때만(연결 끊김·시간 초과·5xx·409) | 토큰만 | 구현됨 |
| `PATCH /personas/{id}` | SC-13 이름 수정, SC-07 호칭 저장 | `display_name` 또는 `provider_address` | PR #117 제안, 백엔드 라우트 없음 |
| `GET /personas/{id}/style-profile` | SC-07 열기, 당겨서 새로고침, 분석 중 자동 확인, "다시 시도" | 토큰만 | PR #117 제안(응답 `{profile, analysis}`), 백엔드 라우트 없음 |

| `POST /sessions` | 새 대화 시작 | `persona_id`, `session_id`, `ai_notice_ack_at` | 구현됨 |
| `GET /sessions`, `GET /sessions/{id}`, `GET /sessions/{id}/turns`, `DELETE /sessions/{id}` | 대화 탭·최근 대화 | 토큰만 | 앱은 호출하지만 백엔드 라우터에 없음([SC11.md](SC11.md) 참고) |
| `POST /chat/text`, `/chat/voice`, `/chat/turns/{id}/tts` | 대화 | 메시지·음성 | 구현됨 |

**라우트가 없을 때.** 백엔드에 위 세 제안 라우트가 없습니다.
- 실서버에서 SC-07을 열면 "말투 프로필을 불러오지 못했어요."가 나옵니다.
- 이름·호칭 저장과 다시 분석은 일반 실패 안내가 나옵니다.
- "서버 준비 전" 같은 별도 안내는 두지 않았습니다.

**만들기 요청.** 이름 저장이 불확실하게 끝나면 같은 `persona_id`를 조회해, 이름이 같을 때만 성공으로 처리합니다. 입력 거부(422 `INVALID_INPUT`)·인증 오류는 조회하지 않고 바로 실패로 처리합니다. 이름을 바꿔 다시 저장하면 새 `persona_id`를 씁니다.

**대화 대상.**
- 새 대화는 홈 카드에서 고른 대화 상대의 `persona_id`로 만들어집니다(`startConversation`의 `persona` → `createForPersona`). 고르지 않았으면 목록의 첫 상대를 쓰고, SC-13에서 새로 만든 상대는 바로 선택됩니다.
- 기존 대화를 열 때는 앱이 가진 대화 상대 목록(`PersonaController`)에서 그 대화의 상대를 찾아 지금 이름을 제목으로 씁니다. 그래서 SC-13에서 이름을 바꾸면 기존 대화도 바로 새 이름으로 열립니다.
- 목록에 없는 상대(예: 삭제 중)일 때만 대화 서비스가 알려 준 이름(`Conversation.personaName`)을 씁니다. 이 이름은 대화를 만들 때 저장했거나 대화 서비스가 따로 불러 둔 것이라, 이름을 바꾼 뒤에는 예전 이름일 수 있기 때문입니다. 둘 다 없으면 대화를 열지 않습니다.

**표시 이름과 사용자 호칭(PR #117 제안).**
- 대화 상대 객체의 `display_name`(앱에 표시하고 AI가 부르는 이름)과 `provider_address`(대화 상대가 사용자를 부르는 호칭)를 읽습니다. 미설정·빈 문자열은 `null`입니다.
- 앱은 어디서나 `display_name`이 있으면 그것을, 없으면 `name`을 보여 줍니다(`Persona.label`).
- 수정(`PersonaUpdate`)의 규칙:
  - 바꾸는 필드만 보냅니다.
  - `display_name`은 지우는 요청을 만들지 않습니다. 계약에 `null`로 되돌리는 방법이 없기 때문입니다.
  - `provider_address`는 빈 칸을 `null`로 보냅니다.
  - 응답의 대화 상대로 목록의 해당 항목만 바꾸고, 선택은 유지합니다.
- `data_revision`은 읽어 두지만 아직 쓰지 않습니다.

**이름이 서버에 필요한 근거.** `POST /personas`의 `name`은 필수입니다. 개인화 대화 생성 요청(`contracts/backend-ai/api-spec.md` 3장)에도 `persona.display_name`(1~50자)이 필수입니다. 지금 동작하는 baseline 대화에서는 이름을 쓰지 않습니다.

## 더미 인증(미리보기)

- 더미 인증으로 로그인하면 메모리 구현(`MemoryPersonaService`, `MemoryConversationService`)을 쓰고 백엔드로 요청을 보내지 않습니다.
- 대화 상대는 비어 있는 상태로 시작하므로, 실서버 계정과 같은 이름 설정 흐름을 거칩니다.
- 이름 수정과 호칭 저장은 메모리에 반영됩니다.
- 말투 프로필:
  - 더미 계정에는 기록이 없습니다. 그래서 SC-07은 항상 "아직 분석한 기록이 없어요"를 보여 줍니다.
  - 분석 요청은 서버처럼 422(확정 기록 없음)로 거부합니다.
  - 미리보기용 가짜 프로필은 만들지 않았습니다. 항목 표시·분석 상태는 테스트의 가짜 서비스로만 확인합니다.
- 데이터는 이번 로그인 동안만 메모리에 있습니다.

## 남은 일

1. **백엔드·DB**
   - `PATCH /personas/{id}`, `GET …/style-profile`(`{profile, analysis}`), `POST …/style-profile/analysis` 라우트가 필요합니다.
   - `display_name`·`provider_address` 컬럼과 분석 작업 저장도 필요합니다.
   - PR #117은 계약 문서만 바꾸므로, 병합돼도 이 작업이 따로 필요합니다.
2. **PR #117 답변 반영**: 다음 질문에 답이 오면 화면과 문서를 맞춥니다.
   - `display_name`을 `null`로 되돌릴 수 있는지
   - `stale`을 앱이 구분할 수 있게 할지
   - 분석 중 상태 확인 주기와 상한
   - 반영 실패 뒤 재요청 API
3. **실제 기록 서비스 연결**: 기록은 대화 상대별로 나뉘었지만, 기본 앱은 아직 미리보기 기록을 씁니다. 실제 `ApiRecordService`를 쓸 때는 `recordServiceFactory`가 받은 대화 상대 id로 만들면 됩니다. `null`(계정 전용)일 때 무엇을 만들지는 계정 삭제 계약(`DELETE /account`, 미정)이 정해진 뒤 정해야 합니다.
4. **프로필 삭제**: 설정 화면을 만들 때 다룹니다. 서버에 대화 상대 삭제 API가 없습니다.
5. **대화 상대 선택**: 홈 카드의 선택 목록만 있습니다(별도 화면은 #89 후속). 대화 서비스와 대화 상대 서비스가 각각 `GET /personas`를 호출하는 중복이 남아 있습니다. 화면에 보이는 이름은 이제 대화 상대 서비스 쪽만 쓰므로 이름이 어긋나지는 않지만, 같은 목록을 두 번 불러오는 비용은 그대로입니다.
6. **실서버 통합 검증**: 하지 않았습니다.
