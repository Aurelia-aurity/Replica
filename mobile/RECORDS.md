# 이슈 #9: 기록 업로드·목록

SC-03 화면기획서와 사용자가 제공한 `api-spec.md`(2026-10-13 앱↔백엔드 초안)를 기준으로 구현했습니다. 명세의 기록 API는 제안 단계이며 원본 파일 전송 방식과 용량 제한은 미정입니다. 이 문서는 실제 서버 연동 완료나 팀 합의를 뜻하지 않습니다.

## 실행과 화면

2026-10-30 SC-03·SC-04 UI 반영: 둥근 유형 필터, 파일명 오른쪽 상태·재시도, 목록 하단 확정 안내를 배치했습니다. 업로드는 텍스트·음성 종류 카드, 파일 카드의 ‘변경’, 녹색 동의 카드, 하단 고정 ‘올리기’로 구성합니다. 종류에 맞게 시스템 선택기의 허용 형식을 제한하고, 종류를 바꾸면 선택 파일과 동의를 초기화합니다. 뒤로가기와 ‘취소하고 돌아가기’는 파일을 선택하지 않아도 사용할 수 있습니다. 화자 추출·선택은 준비 안내를 표시하며, 카카오톡 여부나 화자·메시지 수를 임의로 표시하지 않습니다. 합성 화면은 [화면 미리보기](docs/screenshots/issue9/README.md)에 있습니다.

기존 미리보기 계정으로 로그인한 뒤 하단 **기록** 탭에서 시작합니다. **올리기** 또는 빈 목록의 **첫 기록 올리기** → 파일 선택 → 자료 사용 권한·개인화 처리 동의 → 올리기 → 목록 보기 순서입니다.

- 시스템 파일 선택기를 사용해 `.txt`, `.wav`, `.mp3`, `.m4a`를 선택합니다. 취소하면 기존 선택을 유지하고, 형식·빈 파일·이름 255자·용량을 전송 전에 검증합니다.
- 선택한 파일명·확장자·크기를 표시합니다. 새 파일을 선택하면 동의를 해제하며, 동의 없이는 업로드할 수 없습니다. 동의 문구는 개인화 처리와 자료 사용 권한을 확인하고 모델 학습은 포함하지 않습니다.
- 업로드 대기 중 중복 전송·파일 변경·동의 변경·뒤로 이동을 막습니다. 실패하면 같은 UUID·동의 시각·버전을 유지해 재시도합니다. 재시도 불가 오류는 전송 버튼을 비활성화합니다.
- 전체·텍스트·음성 필터에 개수를 표시하고 생성 시각 내림차순, 같은 시각에는 ID 내림차순으로 정렬합니다. 파일명·종류·크기·업로드일을 표시하며, 실제 길이 값이 있을 때만 음성 길이를 표시합니다.
- 목록 로딩·실패·빈 목록·필터 결과 없음·재조회·아래로 당겨 새로고침을 제공합니다. 업로드 후 목록 재조회에 실패해도 업로드 성공은 유지합니다.
- 미리보기는 파일 내용을 읽거나 서버로 전송하지 않고 파일 정보만 세션 메모리에 보관합니다. 앱 재시작·로그아웃·계정 전환 시 목록과 선택 초안이 초기화됩니다. 실제 자료 대신 합성 자료 또는 공유 권한이 있는 자료로 확인하세요.
- **25 MiB는 미리보기 검증용 값**이며 서버 한도로 합의된 수치가 아닙니다. 실제 서비스에는 합의한 `RecordPolicy`를 필수 주입합니다.

## API 준비

`ApiRecordService`는 기본 앱에서 사용하지 않는 교체 가능한 초안 어댑터입니다. 실제 인증 서비스, HTTP 클라이언트, 검증된 기본 URL, 선택한 상대 ID, 정책과 파일 전송 구현이 모두 필요합니다. `ReplicaApp.recordServiceFactory`는 로그인 세션마다 독립된 서비스를 만들어야 합니다. HTTP 클라이언트의 생성·해제는 주입한 쪽에서 관리합니다.

| 단계 | 초안에 따른 동작 |
| --- | --- |
| 예약 | `POST /records`, UUID·상대 ID·파일 정보·동의 시각·버전 전달. `user_id` 미전달 |
| 예약 결과 불명 | 같은 UUID로 `GET /records/{id}` 조회. 404일 때만 같은 ID로 예약 재시도 |
| 원본 전송 | `RecordFileTransport.ensureUploaded` 주입 필요. 이전 결과 불명 상태를 확인하고 원본 덮어쓰기·중복 전송을 방지하는 책임 포함 |
| 완료 알림 | `GET /records/{id}`로 상태 확인 후 아직 `uploading`이면 `POST /records/{id}/uploaded`. 전송 완료 단계는 재전송하지 않음 |
| 목록 | `GET /records?persona_id=...&limit=100&offset=...`, 페이지를 이어 읽고 ID 중복과 `deleting` 제외 |
| 인증·오류 | 요청마다 인증 헤더 획득, 30초 타임아웃, 기존 `BackendService`의 401 세션 해제·이전 세션 결과 폐기. 서버 원문은 화면에 노출하지 않음 |

파일 전송 URL·버킷·서버 경로를 앱에서 추정하지 않습니다. 파일 전송 구현에는 인증·원본 재확인·시간 제한·결과 불명 시 복구를 함께 구현해야 합니다. 앱 재시작 후 중단 업로드 복구는 이번 범위에 포함하지 않습니다.

## SC-03 상태와 후속 합의

| 서버 상태 | 목록 표시 |
| --- | --- |
| `uploading` | 업로드 중 |
| `uploaded` | 처리 대기 |
| `processing` | 음성: 전사 중 / 텍스트: 처리 중 |
| `ready` | 확인 필요 |
| `failed` | 실패 |
| `deleting` | 목록에서 제외 |

`ready`만으로 확정·말투 프로필·검색 색인 반영을 증명할 수 없어 **반영됨**으로 표시하지 않습니다. 확정·반영을 증명하는 응답 규격을 합의한 뒤 연결해야 합니다. 전사 확인(SC-05)과 상세·삭제(SC-06)는 이슈 #10·#11 범위라 현재 항목 탭 시 안내를 표시합니다.

전사 실패 항목의 재시도 API는 초안에 없습니다. 서비스의 `canRetryProcessing`이 참인 경우에만 재시도 버튼을 제공하고 중복 요청을 막으며, 기본 미리보기·초안 어댑터에서는 미제공 안내를 표시합니다. 새 업로드로 기존 전사 실패를 덮어쓰지 않습니다.

실제 연동 전 합의할 항목은 파일 전송 방식·응답 필드·최대 크기, 상대 선택·ID 공급, 동의 문구·버전·저장 방식, 예약의 동일 ID 처리와 지연 응답 복구, 전사 실패 재시도 API, 확정·프로필·색인 반영 표시 기준입니다. 따라서 이슈 #9의 서버 통합 완료 조건은 아직 남아 있습니다.

## 검증

2026-10-28 기준 합성 파일 메타데이터와 모의 HTTP 응답으로 검증합니다. `test/records_test.dart`는 파일 검증 경계, 동의·중복 제출 차단, 같은 UUID 재시도, 예약·완료 응답 유실 복구, 페이지 조회, 빈 목록·필터, 작은 화면·큰 글자, 계정 전환을 검사합니다.

- `flutter analyze --no-pub`: 통과, 문제 없음.
- `flutter test --no-pub`: 전체 57개 통과(기록 기능 9개 포함).
- `flutter build web --no-pub --dart-define-from-file=config/dev.local.json`: 통과.
- 내장 브라우저를 통한 육안 확인: 로컬 서버 연결 시간 초과로 미완료. 화면 테스트는 320×568·글자 배율 1.5에서 긴 파일명을 포함해 넘침 없이 통과했습니다.

파일 선택기는 Flutter 공식 [file_selector](https://pub.dev/packages/file_selector) 1.1.0을 사용합니다. macOS에는 사용자가 선택한 파일의 읽기 권한을 추가했습니다. 기기별 시스템 선택기와 실제 서버 업로드·전사·영구 저장은 별도 통합 검증이 필요합니다. Windows 네이티브 실행은 플러그인의 심볼릭 링크 지원 요구로 현재 환경에서 검증하지 못했습니다. OS 설정은 변경하지 않았습니다.
