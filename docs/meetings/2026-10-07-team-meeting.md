# 2026년 10월 7일 팀 미팅 회의록

10월 2일 멘토 미팅에서는 화면 기획서와 DB 설계를 먼저 구체화하고 10월 12일 중간 발표에서 목표 화면·시스템 구조·각 파트의 진행 상황을 보여주라는 조언을 받았다. 이번 팀 미팅에서는 그에 맞춰 설계 초안과 개발 현황을 확인하고 연동에 필요한 역할과 발표 전 작업을 정했다.

## 화면과 DB 설계

화면 기획서는 수행계획서를 참고해 회의 중 초안을 만들었다. 주요 화면과 동작 흐름을 보여주는 자료로 사용하고 팀 검토를 거쳐 구현할 기능을 정리하기로 했다. 수행계획서만으로는 세부 기능이 충분히 정해져 있지 않아 초안을 검토하며 구현 범위를 정리하기로 했다.

DB는 기존 ERD 자료를 함께 검토했다. 이를 출발점으로 임재성이 필요한 테이블과 저장·조회 모듈을 정리하기로 했다. 초기 서비스는 사용자가 고인의 기록을 올려 대화하는 흐름을 우선하고 본인이 생전에 기록을 등록하는 흐름은 이후 고도화 대상으로 남겼다. 원본 대화·음성의 보관 여부와 TTS 결과의 저장·접근 제한은 논의했으나 보관·삭제 기준은 더 정해야 한다.

## 개발 현황과 연동 준비

김태환은 학교 GPU에서 Qwen2.5 계열 7B 모델을 설치하고 실행한 결과를 공유했다. 윤서준은 AWS 서버를 열어봤다고 설명했다. 각 파트의 준비는 시작됐지만 서로 어떤 기능을 맡고 어떤 형식으로 데이터를 주고받을지는 아직 구체화가 필요했다.

특히 DB·백엔드·AI의 담당 경계가 모호해 다음과 같이 역할을 조정했다.

| 담당 | 역할 |
| --- | --- |
| 김태환 | 프로젝트 진행, 협업 도구·공통 CI, AI 개발·통신 |
| 김민균 | Flutter 프론트엔드와 화면 기획서 |
| 윤서준 | 프론트엔드와 백엔드의 API·통신 연동 |
| 임재성 | DB 설계·저장·조회 모듈, 이번 중간 발표 준비·발표 |

파트 간 호출 규격을 맞추고 백엔드는 공통 main.py에서 각 담당자의 모듈을 import하는 방식으로 나누기로 했다. 같은 파일을 여러 사람이 크게 수정하며 생기는 충돌을 줄이려는 방향이다.

개발 환경은 Flutter 3.47.5, Python 3.12 계열, FastAPI 0.142.1을 기준으로 정했다. Android를 우선 대상으로 하고 AWS 배포 전에는 Docker와 로컬 Supabase로 확인한다. AWS 백엔드 접속 포트는 8000을 사용한다. Python 패치 버전과 Docker·Supabase 버전은 추가 확인이 필요하다.

## 협업 도구와 작업 흐름

각자의 작업을 공유하기 위해 이슈 기반 협업 절차를 맞췄다. 기능·작업 목표별로 브랜치를 만들고 의미 있는 변경 단위로 커밋한 뒤 PR로 검토·병합한다. 정기 회의일까지 PR을 기다릴 필요는 없으며 PM과 관련 파트 담당자에게 리뷰를 요청한다. 다음 작업은 갱신된 main에서 새 브랜치로 시작한다.

회의 중 이슈 템플릿이 표시되지 않는 문제를 해결했고 Notion의 첫 이슈 반영과 한국어 라벨을 확인했다. GitHub에서는 이슈·PR·담당자·라벨을, Notion에서는 일정과 작업 상태를 관리한다. 이후 정기 회의에서는 각 이슈를 기준으로 지난 계획 대비 결과, 막힌 부분과 다음 작업을 공유한다.

회의 후 확인에서는 회의록·발표 자료·설계서도 산출물 단위로 이슈·PR을 진행하기로 정했다. 같은 작업의 작은 수정은 기존 이슈·PR에 모은다.

## 발표 준비와 다음 작업

화면 기획서와 ERD를 검토·보완하고 각 파트의 개발 이슈를 등록해 작업을 시작한다. 프론트엔드·백엔드·DB·AI의 API 연동은 담당자끼리 호출 규격을 맞추며 진행한다.

| 작업 | 담당 | 시점 |
| --- | --- | --- |
| 화면 검토·DB 설계 수정·개발 이슈 등록 | 각 담당자 | 회의 후부터 |
| 개발 진행 상황·자료를 GitHub에 푸시 | 전원 | 10월 9일 금요일 저녁 |
| 화면 기획서·ERD 등 발표 자료 공유 | 관련 담당자 | 발표 자료 작성 전 |
| 중간 발표 자료 작성·발표, LMS 발표자 등록 | 임재성 | 10월 12일 월요일 발표에 맞춰 준비 |
| 다음 정기 팀 미팅 | 전원 | 10월 14일 수요일, 시각 미정 |

금요일 저녁까지 푸시하는 것은 발표자가 각자의 진행 상황을 확인하도록 하기 위한 것이다. 모든 기능의 개발과 PR·병합을 그때까지 마치는 일정은 아니다.

필수 리뷰 승인 수·병합 방식·브랜치 명명 규칙, STT·TTS의 최종 담당과 파트 간 호출 규격은 별도로 정한다.
