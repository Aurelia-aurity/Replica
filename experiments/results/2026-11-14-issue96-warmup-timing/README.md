# 이슈 #96 준비 완료 전 워밍업 및 구간별 지연 측정 결과

이 문서는 이슈 `#96`과 PR `#116`(병합 커밋 `39b76dbc434d354dda248d3960b42328e3d3d7c5`)에서 수행한 학교 GPU 워밍업 검증, 워밍업 전후 첫 요청 지연 비교, 구간별 처리 시간, 첫 토큰까지의 시간(TTFT), 동시 요청 1/2/4건 측정 결과를 정리한다. 구현과 실행 절차는 [experiments/warmup_timing/README.md](../../warmup_timing/README.md)와 [ai/README.md](../../../ai/README.md)를 참고한다.

## 1. 목적 및 측정 환경

2026-11에 측정한 값(이번 작업 이전)은 모델 적재 156.58초, 첫 생성 21.075초, 이후 짧은 JSON 응답 p50 1.516초, p95 1.722초였다. 첫 사용자 요청에 반영되는 첫 생성 지연을 줄이기 위해 준비 완료 전에 합성 요청으로 워밍업을 수행하고, 구간별 지연과 동시 요청 동작을 측정했다. 모델 적재 시간 자체는 워밍업으로 줄지 않으며, 서빙 엔진 교체와 모델 변경은 범위에서 제외했다.

두 차례 모두 학교 GPU(`NVIDIA RTX A6000`, 51041271808 bytes)에서 `Qwen/Qwen3-8B`(revision `b968826d9c46dd6066d109eabc6255188de91218`)를 사용해 합성 요청만 실행했다. 설정은 Persona 모드, greedy, non-thinking, `max_new_tokens=160`, AI deadline 없음이며, CUDA 11.8 환경의 Slurm 파티션 `GPU-PARTITION-A`/`GPU-NODE-A`(GPU 1, CPU 4)에서 수행했다. Slurm 노드명은 기록하지 않았다. 절차는 실행 전에 고정했으며, 재측정하거나 제외한 결과는 없다. 두 작업 모두 같은 851건 요청 행렬(근거 0/3/6/10 × 동시성 1/2/4 840건 + 첫 요청 쌍 10건 + 첫 매트릭스 1건)을 사용했다.

## 2. 워밍업 동작과 준비 완료 검증

추론 서버는 모델 적재 뒤 `baseline`과 `persona` 모드에서 합성 요청 3건을 실행하고 출력을 검증한 뒤 `/readyz`가 준비 완료(HTTP 200)를 반환한다. 워밍업 중에는 `/readyz`가 HTTP 503을 반환하며, 워밍업에 실패하면 준비되지 않은 상태로 남고 자동 재시도는 하지 않는다.

- 실제 모델 워밍업 검증: job `55389`에서 6개 프로세스 모두(6/6) 통과했고, job `55817`에서도 6/6회 통과했다.
- 워밍업 중앙값(3회 호출): job `55389`는 5.220초, job `55817`은 4.433초였다.
- 준비 완료 시점 지연: job `55389`는 약 5.1초 늦어졌다(작업 출력 기록 기준 쌍별 `loader-to-ready` 중앙값 5.088초). job `55817`은 작업 출력 기록 기준 쌍별 `loader-to-ready` 중앙값 +4.631초였다.

## 5. 동시성 1/2/4 측정 결과

두 작업 모두 전체 851건 요청 중 HTTP 200은 371건, HTTP 429는 480건이었으며 그 밖의 오류나 누락은 없었다. 측정한 371건은 모두 `finish_reason=stop`으로 종료됐고 출력은 20~22토큰(근거 0건 22토큰, 그 외 20토큰), 입력은 667/1149/1629/2272토큰이었다. 최대 160토큰까지 생성하는 경우의 시간은 측정하지 않았다. 현재 서버는 한 번에 한 건만 생성하고 대기열이 없다(`queue_present=false`, `queue_wait_ms=null`, 이유 `no_queue`). 따라서 대기 시간은 측정되지 않으며, 동시성 2와 4에서 단일 생성 슬롯이 차 있어 초과 요청이 HTTP 429로 반환됐다.

작업 출력 기록에 따르면 두 작업의 동시성별 거절률은 근거 수와 무관하게 동시성 1에서 `0/30` (0), 동시성 2에서 `30/60` (0.5), 동시성 4에서 `90/120` (0.75)이었다.

## 7. 한계 및 유의사항

- **실행 날짜 표기**: Slurm `sacct` 출력은 시간대 표기 없이 job `55389`가 `2026-11-14`, job `55817`이 `2026-11-15`로 나뉘어 표시된다. 사전 점검 시각(UTC) 기준으로는 두 작업 모두 `2026-11-14`이며, 이슈 댓글 게시일도 `2026-11-14`다.
- **표별 출처**: job `55389` 성공 응답 지연 표는 이슈 #96 댓글에만 공개됐고, job `55817` TTFT 표는 PR #116 본문(ms)과 이슈 #96 댓글(초) 양쪽에 공개된 값이다. 반면 4.3절의 구간별 처리 시간 표, 5절의 동시성별 거절률, 5.2절의 job `55817` 성공 응답 지연 표, `loader-to-ready` 중앙값은 작업 출력 기록에서 옮겨 적은 값으로 PR 본문이나 댓글에는 인용되지 않았다. 작업 출력 기록은 저장소에 없으므로 원본 해시로 재확인할 수 있다(job `55389` CRITERIA.md(원본·회수본) `69635f0d78eacbdbecc5492670ccbe8079bdfdd6a9303fbd745c224b4d4ad8cb`, manifest.json `1de24942a17b34add763399cdaa0c8af5cf3a61666eddf500b67255ddc6bc4bc`, 회수 아카이브 `e69d77494dd9e356635594343fa22cd4d050c599e7839009ef1dc4813ba1a4ce`; job `55817` CRITERIA.md `56168b86de270f9f4e48755c7984a41b763d6cb547a20706f1f5911c4b810cc1`, 회수 아카이브 `a0d7e049956d6e4f13717d139ebdd37338b011e888a91d63a0705a9143fe3e2d`, manifest.json `0a0a7dfaa29ef2c0aab3962b9f12bd1b3601332f310ef362a71b15ccfef2b035`). 두 작업 모두 같은 동결 요청 일정(해시 `c254b270f31be2b634b7ce088f8b0e06885df1cd603be728475ccb1be164fd94`)을 사용했다.

## 8. 후속 작업

- **최대 160토큰 전체 생성 시간 확인**: 윤서준의 PR #116 리뷰가 요청한 최대 160토큰 전체 생성 시간(근거 0·3·10개별 p50/p95)은 이번 20~22토큰 측정 값으로 충족되지 않는다.
- **음성 전체 경로 측정 위치 및 담당 이슈 확인**: STT 종료부터 앱 재생까지의 전체 구간 측정 위치와 담당 이슈에 대해 백엔드(임재성, 윤서준)와 합의한 기록을 확인하지 못했다. #7 완료 조건에는 백엔드 담당자와 STT·LLM·TTS 구간별 시간, 앱 전체 소요 시간을 기록하도록 되어 있으나 #7 본문에는 STT 종료~앱 재생 구간의 정의나 측정 위치가 적혀 있지 않고, #20에는 지연 측정 조건이 없다.
- **통합 후 종단 지연 및 시간 제한 검토 (#44)**: EC2와 학교 GPU 통합 뒤 백엔드가 턴마다 저장하는 `llm_ms`를 측정하고, 잠정 60초인 `LLM_TIMEOUT_SECONDS`를 재검토한다.
- **`/readyz` 실패 상태 구분 검토**: PR #116 리뷰에서 제안된 `/readyz` 본문 상태 구분(예: `loading`, `warming`, `failed`)은 계약 변경이 필요하므로 앱·운영 측에 알릴지 함께 결정한다.
